## Problem Statement

The owner reviewed the deployed FFI-clone work (Stages 1-3, plus the first pixel-fidelity fix — PR #358, primary color + service tiles) live against the real FFI reference site and said it still doesn't read as a 1:1 clone. Three more real, concrete visual/structural mismatches exist beyond what #358 fixed, and each one is a *deliberate, already-recorded* Makam decision that diverged from FFI on purpose — not an oversight this spec can fix by simply copying values:

1. **The header has no search bar.** FFI's real desktop header (`DesktopHeader.tsx`) centers a prominent rounded search input between the logo and nav links. Makam's header has never had one — it was never part of any prior stage's scope, not removed or rejected.
2. **The hero has no photo-overlay treatment.** FFI's hero renders text directly over a full-bleed photo with a dark scrim. Makam's hero (`hero.blade.php`) deliberately renders two stacked blocks (a photo band, then a separate text panel below it) — its own doc comment names this explicitly: *"What was not done, deliberately: no scrim, no overlay, no gradient over the photo. The unified hero ... stays out of every stage until OQ-K5 is answered."* OQ-K5 is a real, still-open question in `design-system.md`.
3. **The footer is a dark inverse panel; FFI's is light.** Makam's footer (`bg-primary-900`, white text, single centered column, 3 links) was deliberately upgraded to the dark inverse treatment in an earlier batch (referenced in `layouts/app.blade.php`'s own comment history). FFI's real footer (`Footer.tsx`) is a light `bg-secondary` panel, four link columns plus social icons, dark text.

Additionally, PR #358's color correction (`primary-600`/`primary-700`) hasn't been re-verified against the other seven public pages (wizard, renewal, marketplace, FAQ, akun, cemetery directory, help centre) — Stage 3 ticket 05's own zero-findings audit ran *before* that correction existed, so it never checked against the corrected values.

## Solution

Close all three visual gaps, each resolving its own already-recorded open question honestly rather than silently overriding it, and re-run the seven-page visual audit against the corrected FFI values from PR #358.

1. **Header:** add a search input to the desktop header bar, matching FFI's real shape (`h-10`, `rounded-full`, left search icon, placeholder text) and position (centered between logo and nav links). Wire it to the existing cemetery directory search behavior (`/pemakaman?q=...`, the same query parameter `CemeteryDirectoryIndex` already accepts) rather than inventing new search infrastructure — this is a real, already-built capability the header simply never exposed. Mobile header is unaffected (FFI's own mobile header has no visible search bar either — confirmed by reading `BottomNavBar.tsx`/mobile layout, search is desktop-only in FFI's real code).
2. **Hero:** resolve OQ-K5. Add a scrim token (`--mk-hero-scrim`, a gradient overlay value) to `tokens.css`, record the decision in a new ADR (superseding/resolving OQ-K5, additive per this doc's own convention — never silently deleting the "deliberately not done" note), and add a verification method for text-over-photo contrast that doesn't depend on the specific photo's content (a worst-case guarantee: the scrim's own darkest stop must be opaque/dark enough that white text clears 4.5:1 against it regardless of what's underneath, verified as a floor, not a measurement of the actual photo). Redesign `<x-mk.hero>` to render the heading/CTA over the photo with this scrim, matching FFI's real visual composition — single static image, not FFI's auto-rotating multi-slide carousel (that is JS-behavioral, out of scope, see below).
3. **Footer:** resolve the light-vs-dark divergence in FFI's direction — change the shared footer to a light surface (matching FFI's real `bg-bg-secondary`), reworking its content into FFI's real four-column structure (Informasi / Bantuan / Legal / social) using Makam's own existing links (privacy, terms, bantuan) and honest omissions where Makam has no equivalent (no careers/press page — do not invent one). This directly reverses the "upgraded to inverse-surface treatment" decision layouts/app.blade.php's own comment history records — flagged here explicitly as a real, deliberate reversal per the owner's 1:1 direction, the same way the icon-medallion squircle-to-circle reversal was.
4. **Re-audit** the seven other public pages against PR #358's corrected `primary-600`/`primary-700` values and the `icon-medallion` shape change, since Stage 3 ticket 05's own audit predates both.

## User Stories

1. As a visitor on desktop, I want a search bar in the header, so that I can search for a TPU/TPS location the same way I would on FFI, without hunting for the cemetery directory link first.
2. As a visitor typing a search term in the header, I want it to actually search real cemetery data, so that the search bar is a real feature, not a decorative FFI-lookalike control.
3. As a visitor on mobile, I want the header to stay exactly as it is today (no search bar), matching FFI's own real mobile header, which also has none.
4. As a visitor viewing the homepage hero, I want the heading and CTA to read clearly over the photo, so that the hero reads as one cohesive visual moment the way FFI's does, not two disconnected blocks.
5. As a visitor with low vision or in bright sunlight on a phone, I want the hero's text to stay readable regardless of which photo is behind it, so that a future photo change can never accidentally make the heading illegible.
6. As the product owner, I want the hero's photo-overlay decision recorded in an ADR, so that OQ-K5 is honestly closed rather than silently bypassed, and so a future agent doesn't re-discover the same "deliberately not done" comment and re-litigate it.
7. As a visitor scrolling to the bottom of any public page, I want the footer to visually match FFI's light, multi-column layout, so that the page doesn't end on a jarring dark panel that breaks the FFI-matching visual system established everywhere else.
8. As a visitor looking for a specific link in the footer (privacy policy, terms, help), I want it grouped under a clear category heading the way FFI's footer groups its links, so that I can find it faster than scanning one flat row.
9. As the product owner, I want the footer's real content to stay honest — no invented "Karir"/"Media" pages Makam doesn't have — so that matching FFI's layout never means fabricating pages that don't exist.
10. As a visitor on any of the seven non-homepage public pages, I want the same corrected FFI blue and circular icon badges the homepage now has, so that no page feels like it was left behind by the color/shape correction.
11. As the product owner, I want a real, reported outcome for each of the seven re-audited pages (a finding fixed, or an honest "nothing found"), so that the audit's completeness is verifiable, not assumed.
12. As a visitor using the site with JavaScript disabled or with `prefers-reduced-motion` set, I want the hero's scrim and the header's search bar to both work without relying on animation, matching this codebase's own established no-JS-dependency and reduced-motion disciplines.
13. As a keyboard-only visitor, I want the new header search input and the redesigned footer's links to be reachable and visibly focused in a sensible tab order, so that none of these visual changes strand keyboard navigation.
14. As a screen-reader user, I want the header search input to have a real accessible label (not just a placeholder), and the footer's new column structure to use real heading elements, so that both remain navigable by landmark/heading the way the rest of this codebase already requires.

## Implementation Decisions

- **Header search bar**: a plain `<form>` + `<input type="search">` inside `header.blade.php`'s desktop bar only, styled to FFI's real shape (`h-10`, `rounded-full`, `border`, left-aligned search icon inside the input via absolute positioning, placeholder `"Cari TPU/TPS..."` — Indonesian, matching Makam's own copy voice, not FFI's literal placeholder text). Submits a GET request to `/pemakaman` with a `q` query parameter, reusing `CemeteryDirectoryIndex`'s existing search capability (confirm its exact query-param name and search behavior by reading that controller directly before implementing — this spec does not assume it is exactly `q` without checking). No new search backend, no autocomplete/live-search JS — FFI's own header search is a plain form submit on desktop (confirmed by reading `DesktopHeader.tsx`: `onSubmit`, no debounced live query).
- **Hero scrim + OQ-K5 resolution**: new token `--mk-hero-scrim` in `tokens.css`, a linear-gradient value (e.g., transparent at the top fading to a dark, sufficiently opaque stop at the bottom, where the text sits) — exact stops/opacity decided at implementation time against the new verification method, not guessed here. New ADR recording: the unified hero is now approved, the scrim token's contrast guarantee mechanism, and that this resolves OQ-K5 — written additively, the existing "deliberately not done" note in `design-system.md` stays as historical record with a superseding note added beside it (this doc's own established convention). `<x-mk.hero>`'s root becomes the photo itself with the heading/CTA absolutely positioned over it behind the scrim, instead of the current two-stacked-`<div>` structure. The `image` prop stays required; behavior on a missing image is unchanged (still throws, per the component's existing `heading`-required precedent — decide at implementation time whether `image` should become effectively required too, since a scrim with no photo underneath makes little sense, or whether the component keeps a two-block fallback for the no-image case). FFI's auto-rotating multi-slide carousel (Framer Motion, touch/swipe, dot indicators, `autoPlayInterval`) is explicitly NOT built — this spec's scope is the hero's static visual composition, not its JS behavior; a future spec can reconsider the carousel separately if wanted.
- **Footer**: change the shared footer's surface from `bg-primary-900`/inverse text to a light surface token (`bg-neutral-100` or equivalent already in `tokens.css` — confirm the exact existing token name at implementation time rather than inventing one) with `text-neutral-900`/`text-neutral-600` for body/secondary text, matching FFI's real light-panel treatment. Restructure into FFI's real column groups, using only Makam's own existing destinations: an "Informasi" or equivalent group is NOT populated with invented pages — Makam has no About/Careers/Press pages, so this spec's footer keeps only the columns Makam has real content for (a "Bantuan" group: FAQ, Bantuan/Kontak; a "Legal" group: Privasi, Syarat & Ketentuan) rather than forcing FFI's exact four-column count. Company name/address (already rendered today via `CompanyInfo`) stays present. Whether to keep or drop the social-icon row is an implementation-time decision — Makam has no established social accounts referenced anywhere else in this codebase, so inventing icons/links to accounts that don't exist is out of scope; the row is dropped unless a real Makam social presence is confirmed to exist.
- **Seven-page re-audit**: same method as Stage 3 ticket 05 (grep for hardcoded hex/px values outside `tokens.css`, arbitrary Tailwind values without a `var(--mk-*)` wrapper, any remaining pre-fix component API usage), re-run against the current `tokens.css`/`icon-medallion.blade.php` state (i.e., after PR #358 merges) rather than the pre-#358 baseline ticket 05 checked. A page where every check comes back clean is a real, valid, reportable outcome — not a skipped step.

## Testing Decisions

- **The seam for the header search bar and footer is the homepage's existing HTTP-level route test**, `tests/Feature/Livewire/Public/HomePageRouteTest.php` (`$this->get('/')`) — the shared layout's header/footer render identically on every page, and this is already the established seam for asserting shared-layout content (see how the bottom-nav and secondary-CTA work earlier this project both extended this same file). Assert: the search form's real markup (input type, name attribute, action target), and that submitting it with a real query string reaches `CemeteryDirectoryIndex` with the expected results (a second, real HTTP request in the test, not just markup presence). Footer: assert the new column structure's real headings and links, and that the removed dark-surface classes (`bg-primary-900`) are genuinely gone, not just that new classes were added alongside them.
- **The seam for the hero redesign is the existing component-level test**, `tests/Feature/View/Components/MkHeroTest.php` (`Illuminate\Support\Facades\Blade::render()`), following this repo's own established pattern for `<x-mk.*>` primitives (`MkCardTest`, `MkIconMedallionTest`, `MkSkeletonTest`, `MkBottomNavTest`). Cover: the scrim renders, the heading/CTA render over it (not below it), the component's behavior when `image` is present vs the decided fallback behavior when absent, and the new contrast-verification method's own worst-case guarantee (a dedicated test or a `verify-contrast.py`-style script assertion, decided at implementation time based on how the guarantee is actually implemented).
- **The seam for the seven-page re-audit is each page's own existing HTTP-level route test**, named explicitly, same as Stage 3 ticket 05: `BookingWizardRouteTest`, `RenewalStartTest`, `MarketplaceIndexRouteTest`, `FaqIndexRouteTest`, `AkunIndexRouteTest`, `CemeteryDirectoryIndexRouteTest`, `HelpCentreRouteTest`. No new seam — this is a verification pass, not new functionality, and every one of these seams already exists.
- **What makes a good test here**: assert real rendered HTML/behavior against real requests, matching this codebase's own established discipline throughout this entire project — never mock the search query, never assert markup presence without also asserting the removed old markup is genuinely gone (the same "assert the negative, not just the positive" discipline PR #358's own test rewrites already established for the service tiles).
- **Prior art**: `HomePageRouteTest`'s own existing secondary-CTA and bottom-nav test methods (added this project, same file) are the direct template for the header/footer assertions. `MkHeroTest.php`'s existing structure is the template for the hero test additions. `docs/design/verify-contrast.py` is the template for whatever the new worst-case scrim-contrast verification method turns out to be.

## Out of Scope

- **FFI's auto-rotating hero carousel** (multi-slide, Framer Motion transitions, touch/swipe, dot indicators, configurable interval) — explicitly not built; this spec's hero scope is the static visual composition only. A future spec can reconsider the carousel separately.
- **A live/autocomplete search experience** in the header — the search bar submits a plain GET request on desktop, matching FFI's own real behavior exactly (confirmed by reading its source, not assumed); no debounced live-query JS is introduced.
- **Inventing Makam pages that don't exist** to fill out FFI's exact footer column count (About/Careers/Press) or FFI's exact social-media presence — the footer keeps only the columns and links Makam has real content for.
- **Mobile header search** — FFI's own real mobile header has no visible search bar either (confirmed by reading its layout source); this spec does not add one to Makam's mobile header.
- **`AGENTS.md`'s four-primary-service-card rule, Makam's own copy/content, page structure/step-count of the booking wizard/renewal/marketplace** — none of this spec's three items touch any of these; all remain exactly as every prior stage of this project already established.
- **The seven-page re-audit finding and fixing anything beyond hardcoded-value/stale-API drift** — if the audit surfaces something structurally bigger (e.g., a page that needs the same kind of card/tile redesign the homepage got), that is a new, separate finding to report and scope later, not silently absorbed into this spec.
