## Revision note — 20 August 2026, `/akun` customer account area (PRs #112/#113/#114)

The `/akun` account area shipped across three sequential PRs on 20 Aug 2026: auth foundation —
login, registration, logout, password reset (PR #112, `lane/akun-auth-foundation`); the account
shell, header wiring, and draft-resume list (PR #113, `lane/akun-shell-and-drafts`); and the
order list closing the account area's fourth tile (PR #114, `lane/akun-pesanan`). New rows are
minted below — PUB-097…PUB-105 — because this work had no owning kiro spec at all (it began from
a plan-mode session, not a spec batch), the same screen-ID-less-by-design situation P4/P5a's
revision notes above already establish a precedent for.

**`POST /keluar` (logout) is deliberately NOT a row.** It has no GET route and renders nothing —
a pure state-mutating redirect (CSRF-protected POST, matching this repo's `DisableMfaController`/
`RecordPaymentReversalController` house pattern for a state change with no screen of its own).
Consistent with this file's own scope: a screen inventory lists renderable states, not actions.

**PUB-050 ("Customer order status") is untouched and remains a distinct, still-unbuilt screen.**
It is the per-order detail/timeline view at `information-architecture.md`'s reserved
`/pesanan/{orderReference}` path — nothing in the `/akun` account area builds it. PUB-103 below
(`/akun/pesanan`) is the account-scoped **list** of a customer's own orders, a different screen
that deliberately does not link to PUB-050 (its own row states why: linking to a route that
doesn't exist would either 404 or, for the one existing order-detail surface that does exist,
`/marketplace/pesanan/{orderNumber}`, point at the wrong order concept entirely — marketplace
orders, not booking orders). Recorded here rather than left for a reader to assume PUB-103
supersedes PUB-050 — it doesn't; PUB-050 stays open.

**PUB-102's "resume by proven ownership" is a deliberate, narrow reversal of a prior security
ruling**, not new default behavior for every draft. `App\Domain\Booking\BookingDraftBinding`'s
own class doc block used to rule out cross-device/cross-session draft resume entirely
("deliberately session-only... cross-device resume is NOT a requirement") — a ruling that
predates customer accounts existing at all. `BookingWizard::resolveDraftById()` (PR #113, Task 1)
now additionally accepts an authenticated `$candidate->user_id === auth()->id()` match as proof,
re-issuing the session binding on a successful rescue — a guest, or an authenticated non-owner,
still fails closed exactly as before. This was surfaced to and decided by the user directly
during PR #113's whole-branch review, not decided silently in code.
