## Preconditions — do not proceed until all are true

1. **DNS ownership confirmed.** `sprint-plan.md` line 493: *"DNS ownership must be confirmed before any record change — ambiguity is an explicit pause condition."* Identify who controls the `makam.co.id` DNS zone and get their explicit sign-off before creating any record. This runbook does not assume that confirmation has happened.
2. **DNS record exists and has propagated.** Staging needs an `A` record (or `CNAME` to the same target dev already uses, whichever the zone owner prefers — mirror however `dev.makam.co.id` was configured, since that is the working precedent on this domain) for `stg.makam.co.id` pointing at the combined dev/staging host's public IP. This is a DNS-changing action; the preparing agent did not make it and has no visibility into whether it has been made. Confirm with:
   ```bash
   dig +short stg.makam.co.id
   dig +short dev.makam.co.id   # known-good comparison, already resolves
   ```
   Do not proceed to Certbot issuance until `stg.makam.co.id` resolves to the expected host IP.
3. **`stg-placeholder` service is listening on `127.0.0.1:8082`.** Per `/opt/makam/compose/compose.yml` on the host (referenced by the task brief; not independently verified by the preparing agent — confirm on the host):
   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8082/
   ```
4. **`nginx -t` passes on the current live config**, before any change, to establish a known-good baseline:
   ```bash
   sudo nginx -t
   ```

## Step 1 — Back up the current nginx config

Do this before touching anything, so there is a rollback path if the new vhost breaks the live apex or `dev.makam.co.id`.

```bash
sudo mkdir -p /opt/makam/backups/nginx
sudo cp -a /etc/nginx /opt/makam/backups/nginx/etc-nginx-$(date +%Y%m%d-%H%M%S)
```

## Step 2 — Confirm the apex is healthy before any change (pre-change baseline)

`makam.co.id` is **live**. Capture its current behaviour before touching nginx so any regression is attributable to this change.

```bash
curl -sS -o /dev/null -w 'makam.co.id: %{http_code}\n'     https://makam.co.id/
curl -sS -o /dev/null -w 'www.makam.co.id: %{http_code}\n' https://www.makam.co.id/
```

Both must return `200`. If either does not, stop — the apex is already unhealthy and this change must not proceed until that is understood and resolved separately.

## Step 3 — Generate the basic-auth credential file (staging access control)

`dev-staging-environment.md` §5 requires staging to remain access-restricted; ADR-0031 explicitly does not extend to `stg.makam.co.id`. The vhost in this batch uses HTTP basic auth — the mechanism the variables file (`ai-agent-dev-stg-setup-variables.env.example`) actually supports today (see **Finding** below). No credential is generated by the preparing agent; a human runs this on the host:

```bash
# First user (creates the file):
sudo htpasswd -c /etc/nginx/.htpasswd-stg <stakeholder-username>
# Additional users (omit -c so the file is not recreated):
sudo htpasswd /etc/nginx/.htpasswd-stg <another-stakeholder-username>
```

Choose credentials out-of-band and distribute them only to the stakeholders who need UAT access, per §5 ("limited stakeholder/UAT access"). Do not commit the resulting `.htpasswd-stg` file or any password to this repository.

## Step 4 — Install the vhost file

```bash
sudo cp docs/operations/examples/nginx/stg.makam.co.id.conf \
        /etc/nginx/sites-available/stg.makam.co.id.conf
sudo ln -s /etc/nginx/sites-available/stg.makam.co.id.conf \
           /etc/nginx/sites-enabled/stg.makam.co.id.conf
```

The vhost as prepared references a certificate at `/etc/letsencrypt/live/stg.makam.co.id/` that does not exist yet (Step 5 creates it). This mirrors how `dev.makam.co.id.conf` was deployed: the file is installed inert, then Certbot's `--nginx` mode or a temporary HTTP-only server block issues the first certificate. Confirm the same pattern was used for dev before proceeding, and use whichever of the two options below matches it:

**Option A — if Certbot was pointed at a temporary HTTP-only block for dev:** comment out (or temporarily remove) the `server { listen 443 ... }` block's `ssl_certificate` lines and the entire 443 block until the first certificate exists, then run `nginx -t` and reload before issuance.

**Option B — if `certbot --nginx` handled the rewrite for dev:** install the file as-is; Certbot's nginx plugin edits it in place during issuance (Step 5) rather than requiring a manual inert stage.

Do not guess between these — check how `dev.makam.co.id` was actually issued and repeat the same option for consistency and so the two vhosts don't diverge in structure.

## Step 5 — Test config and reload

```bash
sudo nginx -t
sudo systemctl reload nginx
```

If `nginx -t` fails, stop. Do not reload. Restore from the Step 1 backup if a reload was already attempted and broke something:

```bash
sudo cp -a /opt/makam/backups/nginx/etc-nginx-<timestamp>/* /etc/nginx/
sudo nginx -t && sudo systemctl reload nginx
```

## Step 6 — Apex regression check (mandatory, per batch brief)

Immediately after the reload, re-run the exact same checks as Step 2 and compare:

```bash
curl -sS -o /dev/null -w 'makam.co.id: %{http_code}\n'     https://makam.co.id/
curl -sS -o /dev/null -w 'www.makam.co.id: %{http_code}\n' https://www.makam.co.id/
curl -sS -o /dev/null -w 'dev.makam.co.id: %{http_code}\n' https://dev.makam.co.id/
```

All three must still return `200`. `makam.co.id` and `www.makam.co.id` regressing is the single highest risk this task carries (`sprint-plan.md` §5 risk table: *"nginx change breaks live makam.co.id — Med / High"*). `dev.makam.co.id` is checked too because it shares the same nginx process and config directory. If any of the three regresses, restore from backup (Step 5's rollback) immediately and stop.

## Step 7 — Issue the TLS certificate

Only after Step 6 passes:

```bash
sudo certbot certonly --nginx -d stg.makam.co.id
# or, if dev used the webroot method instead of the nginx plugin:
sudo certbot certonly --webroot -w /var/www/html -d stg.makam.co.id
```

Use whichever method was actually used for `dev.makam.co.id`, for consistency (see Step 4 note). After issuance, if the 443 block was disabled in Step 4 Option A, re-enable it, then repeat Step 5 (`nginx -t` and reload) and Step 6 (apex regression check) again.

## Step 8 — Verify staging

```bash
# Without credentials — must be refused (401), unlike dev which is public:
curl -sS -o /dev/null -w 'stg (no auth): %{http_code}\n' https://stg.makam.co.id/

# With credentials — must succeed (200):
curl -sS -u '<stakeholder-username>:<password>' -o /dev/null \
     -w 'stg (with auth): %{http_code}\n' https://stg.makam.co.id/

# noindex header present regardless of auth outcome:
curl -sSI https://stg.makam.co.id/ | grep -i x-robots-tag
```

Expected: `401` without credentials, `200` with valid credentials, and an `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` header present on both responses.

## Rollback

```bash
sudo rm -f /etc/nginx/sites-enabled/stg.makam.co.id.conf
sudo cp -a /opt/makam/backups/nginx/etc-nginx-<timestamp>/* /etc/nginx/
sudo nginx -t && sudo systemctl reload nginx
```

Re-run the Step 6 apex regression check after rollback too.

## Finding surfaced, not resolved

`docs/operations/ai-agent-dev-stg-setup-variables.env.example` defines `ALLOWED_DEV_IPS` (an IP-allowlist input for `dev.makam.co.id`) but defines **no equivalent variable for staging** — there is no `ALLOWED_STG_IPS` or similarly named key in that file as of this writing. The batch brief allowed either HTTP basic auth or an IP allowlist keyed off that variables file, "whichever the variables file actually supports." Since only the dev-side allowlist variable exists, this runbook and the accompanying vhost use HTTP basic auth for staging (the same mechanism dev used before ADR-0031) rather than inventing a new variable name. If an IP allowlist is later preferred for staging, add `ALLOWED_STG_IPS` to the variables file first, then swap the `auth_basic` block in `stg.makam.co.id.conf` for `allow`/`deny` directives — the same migration path already documented in that file's own comments.
