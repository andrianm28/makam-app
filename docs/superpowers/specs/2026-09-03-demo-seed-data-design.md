# Demo Seed-Data Subsystem — Design

## Context

The user asked for a full, deep end-to-end UAT sweep across all 9 user roles and every major journey, plus dummy seed data for a **live demo running directly on the real production/beta host** (`makam.co.id`) — confirmed explicitly: no separate demo environment exists, and none will be built for this. This spec covers only the seed-data half. The UAT sweep itself is a separate, already-scoped follow-up (investigation + fixes against the platform as it exists, not a new subsystem) that depends on this seed data existing first, since exercising every journey end-to-end needs real records to click through.

**Why this is architectural, not bounded:** it is a new subsystem spanning eight distinct domains (booking, renewal, marketplace, care subscriptions, certificates/agreements, vendor accounts, cemetery-operator accounts, visitation), it introduces a new cross-cutting safety mechanism (notification suppression), and it changes schema (a new nullable column across several tables) — this is new capability, not an extension of one existing flow.

**The one fact that shapes every decision below:** `makam.co.id` beta is not a sandbox. It already carries real customer bookings and real sandbox payments against real government cemeteries (ADR-0035). Unlike every other environment, its `NOTIFICATION_CHANNEL` is bound to the real `Channels\MailChannel`, not the log-only no-op default. Any seeded record that reaches `SendNotificationChannelJob` with anything resembling a real recipient address triggers an actual send. This spec's central discipline is: seeded data must be indistinguishable from real data to nobody except this subsystem itself, and must never be capable of leaving the platform as a real-world side effect.

## Confirmed decisions (final — do not re-litigate)

1. **Purge marker: a new nullable `demo_batch_id` column** (uuid, indexed) added to every table this subsystem writes to, rather than growing `PurgeExampleDataCommand`'s existing name-list-matching convention. Chosen over the name-list approach because this mechanism touches many more tables than the existing one, and a flag column can never accidentally match a real customer's real data the way a name/slug string comparison theoretically could. This is explicitly a temporary, beta-era mechanism — the column is nullable and inert for all real rows.
2. **Phone convention: `0811-8990-XXXX`**, a structurally valid Indonesian mobile format (passes the same validation `SaveBookingDraftStep`/marketplace checkout already enforce) with the last four digits generated deterministically from a per-record index. Documented in code as a reserved block, "do not dial" — chosen over a deliberately-invalid format specifically so seeded bookings pass the exact same validation real submissions do, which is also better demo fidelity.
3. **Volume: 2–3 records per meaningful status/stage per journey** — enough for an admin/operator list view to show real variety (a booking at DIVERIFIKASI, one at PENAWARAN_TERKIRIM, one completed, one rejected; similarly for renewal/marketplace/care-subscription states) without flooding any dashboard.
4. **Demo account credentials: deterministic and documented.** Every seeded `vendor_users`/`cemetery_operator` login uses the same fixed, clearly-labeled demo password, recorded in this repo's demo-data documentation as intentionally weak, single-purpose, and purged after the demo — not generated-and-shown-once, since this needs to be reliably re-derivable across multiple people who might run the demo.
5. **Execution on beta is a separate, explicit checkpoint.** Merging the PR that adds this subsystem does **not** authorize running it. The seed command must be run manually, once, with the user's explicit real-time go-ahead — this spec only builds and verifies the mechanism locally against disposable Postgres/Redis; it does not run it anywhere live.

## Architecture

### Generator classes — extend the existing `App\Support\ExampleData` namespace, not a new one

One class per domain, matching the existing `CemeteryExampleData`/`VendorListingExampleData` shape exactly (deterministic, index-driven, zero `random()`/`time()` in this subsystem's own generator/selection logic). This determinism claim is about each generator's own field derivation, not a guarantee that a full `demo-data:seed` run is byte-identical end to end: several of the real domain Actions these generators drive (e.g. `CreateSubscription`/`CreateCarePlan`'s `Str::random(8)` reference suffix, and any Action reading wall-clock `now()`) are themselves non-deterministic, and this subsystem intentionally never bypasses those real Actions to force determinism it does not own.

- `BookingOrderExampleData` — booking drafts + orders across states, via `StartBookingDraft`, `SaveBookingDraftStep`, `SubmitBookingDraft`, `VerifyOrder`, `IssueQuoteFromReservedPlot` / `IssueOrderQuote`, `ManualPaymentVerification` / `MarkOrderPaid`, `RejectOrder`, `CompleteOrder` — never a raw `Order::create()`.
- `RenewalExampleData` — via `OpenRenewal`, `QuoteRenewal`, `MarkRenewalPaidExternally` / `MarkRenewalPaidOnline`, `ExpireRenewal` for a mix of live and expired renewal states.
- `MarketplaceOrderExampleData` — via `AddToCart`/`UpdateCartItem`, `PlaceMarketplaceOrder`, `UpdateVendorOrderStatus`, `MarkMarketplaceOrderPaid` — completed, in-progress, and rejected vendor orders.
- `CareSubscriptionExampleData` — via `CreateCarePlan`, `CreateSubscription`, `GenerateCycle`, `CreateWorkOrderFromCycle`/`CreateWorkOrder`, `AssignWorkOrder`, `CompleteTask`, `UploadEvidence`, `AcceptService` (plus one `FileComplaint` case, since CARE-SUB-06's complaint path is real, tested domain logic worth demonstrating).
- `CertificateExampleData` — via `IssueCertificate` (issued + one revoked via `RevokeCertificate`, to show the audit trail). **Scope correction, found during plan-writing (3 Sep 2026):** this generator was originally named `CertificateAndAgreementExampleData` and meant to cover agreements too, via `CreateAgreement`/`AcceptAgreement`. Reading `AgreementType` directly found it has exactly one case, `PreNeedAgreement`, eligible only for a *settled* `PreNeedCase` — a distinct 7-8-action lifecycle (`RegisterPreNeedInterest` through `ActivatePreNeed`) this spec's booking-order generator never produces (it only creates `AT_NEED_SERVICE_ORDER` orders). Agreement seeding is deliberately out of scope for this subsystem rather than built on unverified signatures — see the plan's Task 9 for the full reasoning. A narrower follow-up can add it later if a demo specifically needs the pre-need journey.
- `VendorAccountExampleData` — `Vendor`/`VendorUser`/`VendorListing`/`VendorAvailability` records with real, working login credentials (decision 4). No dedicated domain Action exists for vendor account creation (`Filament\Admin\Resources\Vendors\Pages\CreateVendor` is a plain Filament `CreateRecord` page over the Eloquent model) — this generator creates the models directly, which is consistent with how the app itself does it.
- `CemeteryOperatorExampleData` — a `User` with `ActorRole::CEMETERY_OPERATOR`, granted real scope via `GrantScopeAssignment` to 1–2 of the existing demo cemeteries (never a real one), so the `/operator` panel and plot floor map have something real to show.
- `VisitationExampleData` — via `RequestVisitation`, `ChangeVisitationBookingStatus` across a couple of statuses.

Every generator's public entry point is `seed(string $batchId): void` (or returns created records where a later generator needs to reference them — e.g. `MarketplaceOrderExampleData` needs a vendor from `VendorAccountExampleData`). Every write these generators make carries `demo_batch_id = $batchId` — set via a small shared trait/concern (`Concerns\TaggedAsDemoData` or similar) applied at the point each Action's resulting model is saved, not by modifying the Actions themselves (the Actions stay untouched; tagging happens as a thin wrapper around each generator's own calls).

### Safe-data helpers — one shared source, not eight copies

A new `App\Support\ExampleData\DemoContactData` class centralizes decisions 2 and the email convention: `email(int $index): string` (cycles through `@example.com`/`.org`/`.net`), `phone(int $index): string` (the `0811-8990-XXXX` block), `personName(int $index): string` (the existing "Contoh" convention, extended with realistic-looking Indonesian names so the demo reads naturally — still clearly fictional, matching how `CemeteryExampleData` already does this for cemetery names). Every generator above calls this class for every contact field — no generator invents its own fake contact data.

### Notification safety — defense in depth beyond safe contact data

Correct contact data alone should already prevent a real send (an `@example.com` address bounces/is rejected by any real mail transport). As a second, independent layer: a new `App\Platform\Notification\DemoDataSuppression` — a simple, temporary flag that `demo-data:seed` sets to `true` for the duration of its run and clears in a `finally` block.

**Correction from an earlier draft of this spec, found during plan-writing (3 Sep 2026):** the flag must NOT be checked inside `SendNotificationChannelJob` — that job `implements ShouldQueue` and, outside the test environment, runs on Laravel's real `database` queue driver via a separate `queue:work` worker process (`config/queue.php`'s default, confirmed by reading it directly; only `phpunit.xml` overrides this to `sync`). A flag set in the seed command's own process would be invisible to that worker process entirely — an in-process check there would silently do nothing on beta.

The correct choke point is one step earlier, and it is genuinely simpler: `ConsumeOutboxNotificationJob` (the actual queued/async job) is dispatched by exactly two **plain, non-queued** listeners on the synchronous `OutboxEventPublished` event — `App\Domain\OrderWorkflow\Listeners\DispatchOrderNotifications` (the order-lifecycle bridge) and `App\Platform\Notification\Listeners\DispatchNotificationConsumerOnOutboxEventPublished` (the generic path for every other domain's own catalogued events). Both fire **synchronously, in the same PHP process** that wrote the outbox event in the first place — which, for every write this subsystem makes, is the `demo-data:seed` command's own CLI process. `DemoDataSuppression`'s flag is checked in both listeners, immediately before their `ConsumeOutboxNotificationJob::dispatch(...)` call, and short-circuits (logging that it was suppressed) when set. Because nothing else in the system ever shares that CLI process, this cannot suppress or interfere with any real, concurrent notification for a real customer — it only ever prevents the queued job from being created in the first place for events raised during this one seed run, which is both simpler and strictly safer than trying to intercept the job after it's already queued.

### Orchestration — one command each for seed and purge

- `php artisan demo-data:seed` — generates a batch UUID, runs each generator in dependency order (cemeteries/vendor accounts/operator accounts first; orders/subscriptions/visitation that reference them after) inside per-domain `DB::transaction()` blocks (one domain's failure doesn't corrupt an earlier one's already-committed data), wraps the whole run in `DemoDataSuppression`, and prints the batch id plus a summary count per domain at the end.
- `php artisan demo-data:purge {batchId?}` — defaults to the most recently seeded batch if omitted (reads it from a small marker, e.g. the last row of a `demo_data_batches` log table this command also writes to, so `--batchId` is optional but explicit is always honored). Deletes in FK-safe reverse-dependency order, reusing the same ordering knowledge `PurgeExampleDataCommand` already encodes for the tables it currently covers, extended for the new ones. Requires `--force` to actually run, matching `PurgeExampleDataCommand`'s existing confirmation discipline.

### Schema change

One migration adding nullable `demo_batch_id` (uuid, indexed) to: `booking_drafts`, `orders` (booking's own order model), `renewals`, `care_plans`, `subscriptions`, `agreements`, `certificates`, `vendors`, `vendor_users`, `marketplace_orders`, `vendor_orders` (`App\Domain\Marketplace\Models\MarketplaceOrder`/`VendorOrder` — a genuinely different model/table pair from booking's `orders`, confirmed by reading the migrations directly rather than assumed), `visitation_bookings`, and `users` (for the cemetery-operator demo account) — plus a new small `demo_data_batches` table (`id`, `batch_id`, `created_at`, `summary` json) that `demo-data:seed` writes one row to per run, giving `demo-data:purge` something to default from and giving a human a simple audit trail of what's been seeded when.

## Error handling

Each domain generator's transaction failing aborts only that domain — the command reports which domains succeeded and which failed, with the real exception, rather than a silent partial state. `demo-data:seed` is safe to re-run after a partial failure (a fresh batch id each time; nothing about a failed batch blocks a new attempt). `demo-data:purge` on a batch that seeded exactly zero rows in some domain (partial failure) still cleanly removes whatever real subset exists.

## Testing

- `DemoContactData` — unit tests asserting the email/phone helpers are deterministic and match their documented safe ranges.
- Each generator — a Feature test asserting: the right number of records land in the right states, every contact field uses the safe convention (grep-style assertion over the actual created rows, not just trusting the helper), and `demo_batch_id` is set on every row.
- `demo-data:seed`/`demo-data:purge` — an integration test running seed then purge against real Postgres, asserting the database returns to its pre-seed state (row counts per touched table match), and a second test asserting a mid-run domain failure (forced via the same FK-drop technique this repo's `BookingWizardDegradedReadsTest` already established) leaves earlier domains' data intact and reports the failure honestly rather than silently.
- `DemoDataSuppression` — a test asserting `DispatchOrderNotifications` and `DispatchNotificationConsumerOnOutboxEventPublished` genuinely do not dispatch `ConsumeOutboxNotificationJob` while the flag is set (`Queue::fake()` + `Queue::assertNotPushed()`), and do resume normal dispatch once a seed run completes (including on a thrown exception mid-run, via the `finally` guarantee) — proven by a real notification-triggering Action run immediately after a (deliberately failed) suppressed run, asserting the job IS pushed that time.

All against real Postgres 18/Redis 8.2 via the pinned CI image, never SQLite, per this repo's established practice.

## Out of scope

- The broader full-platform UAT sweep (all roles/journeys, visual UI/UX review) — separate follow-up.
- Actually running `demo-data:seed` against the live beta database — a distinct, explicit checkpoint after this PR merges (decision 5).
- WhatsApp notification safety — the channel isn't live yet; `DemoDataSuppression` is written generically enough to cover it once it is, but no WhatsApp-specific work happens here.
- Fixing `RealisticMarketplacePricingExampleData`'s pre-existing gap (its 3 vendors are missing from `PurgeExampleDataCommand`'s name list) — noted as a real, small, pre-existing bug, but unrelated to this subsystem; flagged for a separate one-line fix, not bundled in here.
